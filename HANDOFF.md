## Browser-verify tips (learned the hard way)

- **Preview MCP screenshots are unreliable for sub-pixel detail.** JPEG compression smears 1-2px features (scanlines, dither stipple) into uniform tints; resize timing can produce thumbnail-sized images that look like rendering bugs. **If a screenshot contradicts intuition, sample canvas pixels via `getImageData` first** — they're more reliable than the screenshot tool for detecting real issues. Even better: ask the user to look in their native browser.
- **A Browser-pane click can land outside the clickable region** in a narrow viewport. When the click "succeeds" but no event fires, fall back to `javascript_tool` with `element.click()`.
- **A mid-fade DOM read can grab the OLD screen.** `fadeOutAndRemove` keeps a disposed screen's DOM in the document for the ~180ms fade, so a `querySelector` right after a scene swap can return the lingering outgoing screen (it once made a correct Turn-1→Turn-2 transition read as "still Turn 1"). When verifying scene-swap UIs, capture **bus-event payloads** (subscribe → drive → read the array) — they're authoritative; don't trust a mid-fade DOM read.
- **The preview MCP duplicates console output 6×** for reasons not yet understood. Log de-duplication is purely cosmetic; the events are still firing once per emit.
- **Force-verifying defeat/victory paths** when natural runs keep winning/losing the wrong way: temporarily add `(window as unknown as { __bus: typeof this.bus }).__bus = this.bus;` to Game constructor, then `window.__bus.emit('battle:ended', { winner: 'enemy' })` or `window.__bus.emit('run:victory', {})` from eval. Remove the hook before committing.
- **`getImageData` on a WebGL canvas can return cleared buffers** if `preserveDrawingBuffer` is false (Three.js default). Read pixels synchronously inside the same frame the render happened, or temporarily set `preserveDrawingBuffer: true` for debugging.
- **Verifying short-duration sprite fades (D5.C-style) is hard via the preview MCP.** Each `javascript_tool` call synchronously blocks the JS main thread, stalling `requestAnimationFrame`. When the next frame fires, `dt` is the full eval+sleep time — easily 100-200ms per frame instead of 16ms — and the renderer's animator drains a 500ms fade in 2-3 frames. The fade IS correctly wired (you can prove it by inspecting `br.animator.fades.size` immediately after the spawn fires), it just visually completes faster than you can screenshot. To capture a clean mid-progress visual: trigger the fade, freeze `br.animator.update` to a no-op, then manually call `sprites.updateSprite(handle, { alpha: 0.5 })` to lock the alpha — that survives across screenshots and evals. Bumping `SPAWN.durationSeconds` to a longer value in `config/spawn.json` is the alternative (and works for any short fade) but requires a rebuild.
- **A backgrounded preview tab throttles `requestAnimationFrame` to ~0, so the Clock-driven sim freezes at `tick 0` and a screenshot times out (the WebGL render loop never goes idle for the capture).** This bit E6's eyeball verification hard. Two workarounds, both via the dev `window.__game` handle (DEV-only, `src/main.ts`): (1) **drive the loop by hand** — `const br = __game.activeScene.battleRenderer; for (let i=0;i<600 && !ended;i++){ br.world.tick(); br.update(1/20); }` advances sim + animations deterministically without rAF (TS `private` fields are runtime-accessible, so `br.world` / `br.animator` / `br.handles` / `br.projectiles` are all reachable). (2) **inspect synchronously** — subscribe to `__game.bus.on('unit:attacked', …)` and read DOM/positions in the handler; the BattleRenderer's handler runs first (subscription order) so the shove/hitsplat/projectile already exists when yours fires. The tab sometimes un-throttles mid-session (becomes active), at which point combat auto-runs to completion on the real loop — don't be surprised if `activeScene` has advanced to PromotionScene between evals; persist probes on `window.__x` so they survive the scene swap. Net: **functional correctness is fully eval-verifiable; subjective feel still needs the user's native browser.**
- **An UNDISPLAYED Browser pane composites nothing — no rAF, the battle clock sits at tick 0, screenshots time out (§82e2, worse than the §79 aspect-NaN case).** The answer that verified a sim+render feature end to end without one screenshot: drive the REAL production loop synchronously — `world.tick()` + `battleRenderer.update(0.05)` in lockstep via `__game.activeScene` — pin the fixture with URL dials (`?roster=catapult:2,…`), and assert on DOM state. (`resize_window` + a `resize` event first if the camera booted with aspect NaN.)
- **`preview_start` returns before the page is live, and the pane's frozen loop stalls the Web Animations API as well as rAF (§96a, §96d, §96.5b2 — four bites in two sessions; papercuts 2026-09-12/13).** A probe fired in the same turn reads UA defaults — `document.styleSheets.length` 0, 13.33px buttons, black text, `window.__game` undefined — and looks like a catastrophic regression; it is nothing. The wait is not a fixed number (7 s was once not enough): `location.reload()` via `javascript_tool` (a `navigate` to the URL the tab already holds can be denied), then POLL until `document.styleSheets.length > 0 && window.__game` before believing any measurement. And an `Element.animate()` in the hidden pane sits at its first `currentTime` with `visibilityState` "visible" while a programmatic `finish()` never fires its event — a timing claim there is wiring only; the flight belongs to the user's eye, or hand-drive the loop as above.
- **The user's tab and your probe tab are different page instances, and yours can't see theirs (§79g).** A days-old tab accumulating Vite HMR patches ran pre-change renderer code against new CSS — a bug no fresh `preview_start` tab could reproduce. When a user-visible symptom contradicts a clean measurement, ask for a hard reload BEFORE hunting the code; a precise symptom fingerprint usually names the superseded code path.
- **Default-seed sampling bias is real (§77e2b): the viz opened on seed 1 — the single worst drifter in a 500-seed corpus.** When an eyeball impression contradicts an instrument, check what the default view happened to show before trusting either.
- **The pane is Chromium; the user is on Firefox — a dev chord "verified" by a synthetic `KeyboardEvent` can be one Firefox owns (§99a: Ctrl+Alt+R is Reader View; gotcha #134).** A new Ctrl+Alt chord clears three sets — the registry's codes, `devKeys.ts`, and the browsers' own — and gets one press in the user's Firefox before it counts. Two more §99 tells: a hidden pane stalls rAF AND the sim (70 s of "battle" ticked zero) — drive `__game.activeScene.tick(1/60)` in a loop (the current loop entry; it walks the countdown + playback, unlike the older `br.world.tick()` recipe) and read call counters wrapped on the prototypes (`Object.getPrototypeOf(activeScene.battleRenderer)`, `__game.renderer`) instead of pixels; and Vite full-reloads the tab when a `.ts` file changes underneath it, so module state (a dev override, a `window.__probe`) silently resets — `performance.getEntriesByType('navigation')[0].type === 'reload'` is the check before blaming code.
- **The pane cannot ACTIVATE a native `<button>` by Enter, parks CSS transitions at their start while hidden, and is Chromium for the Tab order too (§100).** Enter on a focused `<button>` (a map node, a character card) moves nothing — every Enter-on-button route is wiring-only in the pane and the user's Firefox read; a synthetic `KeyboardEvent` DOES run JS listeners (the `pressable()` Enter / Space paths were proven by a click counter on the card — Enter = 1, Space in battle = 0 with pause toggled) but never a native default action. A computed-style read of a `:focus-visible` twin can show NO effect while the rule matches the element — the hidden pane holds the 0.1 s transition at its first frame; take a screenshot (a forced frame) and read again, and control-probe with a hovered sibling before blaming the sheet. Firefox's sequential focus runs off the document into the browser UI where the pane wraps silently — a Tab-order bug (100c1 → 100e2, the chrome column's DOM position) the pane structurally cannot show. And never write a source file mid-sequence: the Vite reload throws the walk back to the character select (100c1 lost a map walk to a prettier pass).
- **The layout instruments (§101) — and the three ways the pane lies about layout.** (1) A hidden pane can be ZERO-WIDTH (`innerWidth` 0): fixed / flex boxes collapse to min-content and text wraps that never wraps for a player — `resize_window` to 1280×720 (+ a `resize` event) before ANY box read, and reset it to `desktop` after. (2) An unseeded `location.reload()` starts a DIFFERENT RUN, so a before/after diff across a reload compares two maps, two encounter names, other cards per slot (101b "found" 60 moved elements that way). Use the SAME-RUN TOGGLE instead: inject a `<style>` that REVERTS the change = "before", remove it = "after", same page, same instant; CSS edits hot-swap without a reload, a `.ts` edit does not. (3) The `ResizeObserver` and every rAF consumer need a FRAME — take a screenshot to force one, and park any real-time clock first (`activeScene.countdown.advance = () => {}`; forced frames let 5 real seconds expire the countdown mid-probe). The two oracles that held: the BOX ORACLE (every visible `#ui *` rect keyed by DOM path, diffed across the toggle — report only what changed OUTSIDE the surface you meant to move) and the CONTENT SWEEP (write a longer value into ONE element, list every OTHER element whose rect moved, restore — 12 of 14 "digit sinks" moved nothing). Mutate nodes production never rewrites (a filler tile), not ones the per-frame refresh resets (the status rows re-hid themselves). Cap a probe's output (`.slice(0, 8)`) — two uncapped diffs cost this session thousands of tokens each.
- **Five small pane facts from Round 7 with no other home (the close sweep).** (1) The pane's `find` cannot see text outside a control (a star run in a plain span) — use coordinates or a DOM query. (2) The desktop app can stop the `dev-preview` server BETWEEN TURNS; the hook's "no preview server is running" line is the tell — budget a `preview_start` per verify turn, not per session. (3) A long synchronous drive can time the TOOL CALL out ("Internal error") while the work completes — read the state before re-driving, and chunk a driver to one battle per call. (4) `?seed=<n>` pins the run (with `?layout=`, `?character=`, `?firstNode=`, `?roster=`): `?layout=isthmus&seed=7&character=soldier` gives an event at node 0 and a battle at node 1 — seed a probe URL instead of diffing across an unseeded reload. (5) A whole screen can be fixtured in one eval on the SAME run through the run's private fields + the bus (set `run.pendingRewards` / `run.rollPortStock(n)`, emit `reward:offered` / `port:entered`); transient DOM (hitsplats) is caught by a `MutationObserver`, not a screenshot (recipe: `archive/post-94-worklog.md` §98d).
